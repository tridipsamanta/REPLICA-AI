SECTION 1 — INTRODUCTION

Hello everyone, respected judges, and members of the panel. Today, we are excited to present our project: REPLICA, an AI-powered voice security, deepfake detection, and speech forensics platform.

Over the past few years, artificial intelligence has made massive progress in generative audio and speech synthesis. Today, deep learning models can clone a person's voice using just a few seconds of recorded audio. While this technology has created incredible creative opportunities, it has also introduced a serious security threat.

Scammers and malicious actors can now generate realistic human voices to commit financial fraud, execute vishing attacks, impersonate company executives, and trick family members during fake emergency calls. Traditional voice authentication systems and human ears can no longer reliably distinguish between an authentic human voice and a synthetic voice clone.

When we looked at existing solutions, we noticed a critical gap. Most tools either run static checks on pre-recorded files or rely on a single classifier that fails when exposed to new synthesis techniques. Furthermore, security teams rarely get actionable explanation models that show why an audio sample was flagged as synthetic.

To solve these security challenges, our team designed, built, and integrated REPLICA. REPLICA is a full-stack, real-time voice forensic command center that detects synthetic speech, monitors live audio streams, provides explainable AI attributions, and verifies cryptographic voice provenance.


SECTION 2 — WHAT REPLICA DOES

Let us look at what REPLICA achieves as an integrated platform.

REPLICA provides four main pillars of protection: Detection, Real-Time Monitoring, Explainable AI Attribution, and Provenance Verification.

First, in Detection mode, users can upload pre-recorded audio files in WAV, MP3, FLAC, or OGG formats. REPLICA processes the audio through our deep learning detection pipeline and outputs a precise classification verdict along with a confidence score.

Second, in Real-Time Monitoring mode, REPLICA continuously listens to an active microphone input or incoming stream. It segments the streaming audio into short windows, evaluates each window through neural models, and streams live security alerts to the user interface.

Third, REPLICA goes beyond simple binary classification by offering Explainable AI. It highlights exact waveform segments and spectral frequency regions that drove the model's decision, answering not just IF a voice is fake, but WHY it was flagged.

Fourth, REPLICA includes a Verification and Watermarking module. It checks for inaudible spectral watermarks and cryptographic C2PA manifests to prove whether an audio sample was synthesized by authorized AI engines.


SECTION 3 — HOW WE DESIGNED THE SYSTEM

Now, let us discuss the high-level architecture of REPLICA.

We designed REPLICA using a decoupled full-stack architecture. The platform consists of three primary layers: the React user interface, the FastAPI backend server, and the PyTorch deep-learning inference engine.

When a user interacts with the web interface, the audio data flows through a structured pathway:
1. The user captures or uploads audio through the browser.
2. The HTML5 Web Audio API processes raw microphone data into sixteen kilohertz mono PCM streams.
3. The frontend sends data to the backend using REST APIs for file uploads or WebSockets for live streaming.
4. The FastAPI backend validates, decodes, and normalizes the audio tensors.
5. The PyTorch inference engine routes the audio through our ensemble of neural detection models.
6. Explainable AI modules generate frame-by-frame attribution scores.
7. The backend packages the verdict, metrics, and visualization heatmaps into JSON payloads.
8. The frontend renders dynamic radar charts, temporal risk heatmaps, and forensic alerts.

Decoupling the frontend, backend API, and ML inference engine was a key design decision. It ensures that heavy GPU and CPU neural model passes do not block the user interface or drop WebSocket connections.


SECTION 4 — FRONTEND DEVELOPMENT

Let us move to the frontend implementation.

We built the REPLICA user interface using React 18 and TypeScript with Vite as our build tool. TypeScript gave us strict type safety for our API schemas, audio buffers, and WebSocket event streams.

To create an intuitive experience, we implemented responsive navigation linking our primary modules: Detect, Live Monitoring, Verify, Synthesis, and Forensic Results.

We paid special attention to visual design. We developed a dual theme architecture using Vanilla CSS variables and TailwindCSS:
- Neon White Light Mode: A futuristic pearl-white base with soft ambient blue-violet glows, subtle glassmorphism, and dark high-contrast typography.
- Cyberpunk HUD Dark Mode: A dark command center aesthetic with vibrant cyan, purple, and emergency red glow indicators.

For the live streaming interface, we integrated the native HTML5 Web Audio API. Using custom AudioWorklet processors running in a dedicated browser thread, we capture raw microphone samples without freezing the UI thread. The audio is resampled to sixteen kilohertz mono PCM and converted to sixteen-bit signed integers.

We stream these PCM chunks over WebSockets to our server. As classification events arrive back, the frontend updates real-time Recharts visualizations, audio-reactive SVG spectral waveforms, and a temporal chunk-by-chunk density timeline.


SECTION 5 — BACKEND DEVELOPMENT

On the backend side, we implemented our application using Python 3.12 and FastAPI running on Uvicorn.

FastAPI provided asynchronous request handling, built-in Pydantic data validation, and native WebSocket support.

Here is how we structured the backend services:
- We created REST endpoints like `/detect` for file upload analysis, `/explain` for attribution, and `/watermark/verify` for provenance checks.
- We created the `/ws/stream` WebSocket endpoint for real-time live mic streaming.
- We built audio validation utilities that inspect file headers and magic bytes to reject corrupted or malicious uploads.
- We implemented OAuth2 authentication with JWT bearer tokens to secure our analysis services.
- We added SlowAPI rate limiting to defend against denial of service attempts.
- We implemented automatic temporary file management with a Privacy Data Protection Law compliant sweep that purges temporary audio files within sixty seconds.


SECTION 6 — AUDIO PROCESSING PIPELINE

Now, let us examine how an audio sample moves through our audio processing pipeline.

When an audio file or stream arrives at the backend, it follows a strict sequence:
1. Format Validation: The system sniffs magic header bytes to verify WAV, MP3, FLAC, or OGG format.
2. Decoding: Using SoundFile and libsndfile, raw compressed audio is decoded into a numeric float array.
3. Channel Downmixing: Multi-channel stereo audio is averaged down to single-channel mono.
4. Resampling: Using TorchAudio, the sample rate is resampled to a standardized sixteen kilohertz rate.
5. Signal Normalization: Amplitude levels are peak-normalized to prevent clipping and volume bias.
6. Silence and Quality Guard: The pipeline runs a Voice Activity Detection and energy check. If the input is silent or near-silent noise, it bypasses model forward passes to avoid false positive predictions.
7. Feature Extraction: For classical pipelines, Librosa extracts Mel-Frequency Cepstral Coefficients, Mel Spectrograms, Spectral Centroids, and pitch contour statistics.
8. Tensor Preparation: For deep learning models, raw acoustic waveforms are formatted into tensors and passed directly to neural encoders.


SECTION 7 — MACHINE LEARNING PIPELINE

Let us look at our machine learning architecture.

No single detection model is effective against every synthesis technique. To achieve high reliability, we integrated multiple complementary model architectures into REPLICA:

1. XLS-R-300M + AASIST: Our flagship production model. It combines Facebook's multilingual XLS-R self-supervised transformer encoder with an AASIST Graph Attention Network backend. It evaluates graph representations of spectral and temporal acoustic relationships.
2. Wav2Vec2 Anti-Spoofing Classifier: We integrated the fine-tuned Wav2Vec2 anti-spoofing architecture, which extracts contextual speech representations from raw audio waves.
3. WavLM Foundation Models: We incorporated Microsoft WavLM Base Plus and WavLM Large encoders for robust feature representation across noisy speech environments.
4. Classical Baseline: We integrated an MFCC-based feature extractor with Scikit-Learn Random Forest and XGBoost classifiers as a lightweight fallback.
5. ONNX Runtime Engine: We formatted model pipelines to support ONNX runtime execution for optimized inference speed.

We want to clarify that we did not train these massive foundation transformer weights from scratch. Instead, our team designed the integration pipeline, configured state-dict state management, implemented dynamic fallback resolution, built tensor batching logic, and engineered the scoring decision layer.


SECTION 8 — REAL-TIME LIVE DETECTION

Let us look closely at how our real-time live detection workflow operates.

When a user opens the Live Monitoring section and clicks "Start Monitoring":
1. The browser requests microphone permission and initializes an AudioContext.
2. An AudioWorklet captures raw mic frames and sends them to a buffer.
3. The frontend resamples audio to sixteen kilohertz PCM and packs it into chunks.
4. The client opens a WebSocket connection to `/ws/stream` and sends a JWT token.
5. The backend accepts the socket, verifies the token, and begins reading binary PCM frames.
6. The backend maintains a sliding four-second audio window.
7. Every two seconds, the backend runs our neural detection pipeline on the active sliding window.
8. If the window contains silence or ambient background noise, our VAD gate returns a clean authentic verdict.
9. If active speech is detected, the neural models calculate the synthetic probability.
10. The backend broadcasts a JSON event containing window ID, classification label, confidence score, and model signature.
11. The frontend receives the event, updates the voice prediction percentage bars, shifts the waveform timeline, and triggers visual threat indicators.


SECTION 9 — DETECT / UPLOAD ANALYSIS

Now, let us trace what happens when a user analyzes a pre-recorded audio file in the Detect section.

1. The user drops a target audio file onto the dropzone or selects it via file picker.
2. The UI creates a local object URL to display the filename, file size, and waveform preview.
3. The user selects their preferred model architecture, such as XLS-R + AASIST or Wav2Vec2.
4. Clicking "Analyze Audio" sends an HTTP POST request containing the multipart audio payload to `/detect`.
5. The backend saves the stream to a temporary storage location and computes a SHA-256 hash.
6. The backend runs header decoding, audio quality checks, and tensor normalization.
7. The selected model runs inference and returns a raw probability score.
8. The backend maps the score into classification categories like Authentic Human Voice or AI Generated Synthetic Voice.
9. If explanation is requested, the XAI engine computes frame-by-frame attribution weights.
10. The backend returns the complete response payload.
11. The frontend renders the verdict badge, confidence dial, spectral risk cards, and timeline heatmap.


SECTION 10 — EXPLAINABLE AI

In cybersecurity and forensics, simply giving a prediction is not enough. An analyst must understand WHY a model arrived at a specific verdict.

To solve this black-box problem, we implemented Explainable AI inside REPLICA:

1. Waveform Attribution: Using Captum's Integrated Gradients algorithm, we calculate the gradients of the model's output with respect to input audio samples. This identifies exact milliseconds of speech that contributed most to the synthetic verdict.
2. Time-Domain Occlusion: For non-differentiable models, we developed a sliding occlusion algorithm. The system systematically silences small audio segments, re-scores the clip, and measures output probability drops.
3. Spectral Analysis: We compute frequency distribution heatmaps that expose high-frequency phase discontinuities and vocoder artifacts that are inaudible to human ears.

When an analyst reviews an XAI result in REPLICA, they see a temporal heatmap showing green for natural human speech transitions and red for anomalous synthetic speech segments.


SECTION 11 — WATERMARKING AND PROVENANCE

Detecting synthetic audio is only one side of the security equation. The other side is active provenance and attribution for legitimate generative engines.

In REPLICA, we implemented a dual-layer watermarking and provenance verification architecture:

1. Custom Spectral Watermarking: When audio is generated in our synthesis engine, we embed a subtle, key-derived spectral watermark into high-frequency bands. The watermark amplitude is kept inaudible while remaining detectable via correlation algorithms.
2. C2PA Cryptographic Provenance: We integrated the C2PA python runtime to attach cryptographic manifests to synthesized audio files. The manifest is signed using ES256 private keys and contains software attribution metadata.

During verification, our `/watermark/verify` endpoint checks both the spectral correlation score and C2PA manifest signatures. If a match is found, REPLICA proves that the audio was created by an authorized AI system.


SECTION 12 — SECURITY AND PRIVACY

Security and privacy were core requirements throughout our design process.

First, authentication is enforced using OAuth2 with signed JWT tokens. Unauthenticated requests to analysis and streaming endpoints are rejected.

Second, to protect against API abuse and denial of service attacks, we configured rate limiting using SlowAPI. API keys and IP addresses are restricted to reasonable request rates.

Third, we prioritized data privacy. User uploads are processed in memory or written to isolated temporary files. Our PDPL auto-deletion background task purges temporary audio files within sixty seconds.

Fourth, input validation enforces file size limits, header verification, and PCM sample bounds to prevent buffer overflows or malicious payload injection.

SECTION 15 — WHAT HAPPENS INTERNALLY DURING THE DEMO

While the user sees smooth visual updates on screen during the demo, here is what is happening behind the scenes in milliseconds:

1. Audio Capture: The browser AudioWorklet captures four-thousand-ninety-six samples of Float32 audio, resamples them to sixteen kilohertz PCM, and streams them over the WebSocket.
2. Server Ingest: The FastAPI WebSocket handler appends incoming bytes to a sliding ring buffer.
3. Preprocessing: Every two seconds, a threadpool task extracts the latest four-second audio window, converts it to a normalized float tensor, and checks for silence.
4. Model Forward Pass: The tensor is passed into our model registry. PyTorch executes tensor matrix multiplications across transformer layers and attention graphs.
5. Softmax Scoring: The raw model logits are normalized via softmax to compute synthetic versus authentic class probabilities.
6. JSON Serialization: The server packages the score, window ID, timestamp, and model signature into a JSON event payload.
7. UI Render: The React frontend receives the WebSocket frame, updates state hooks, re-renders SVG waveform heights, shifts timeline bars, and updates overall threat level styling.


SECTION 16 — WHY OUR APPROACH IS DIFFERENT

Let us summarize why REPLICA stands out compared to standard audio tools:

- Multi-Model Resilience: Instead of relying on a single classifier, REPLICA combines transformer encoders, graph attention networks, and classical ML fallbacks.
- True Real-Time HUD: We stream raw audio over WebSockets with sub-second inference response times, making it usable for live call defense.
- Explainable Attributions: We provide integrated gradients and occlusion timelines so analysts get clear evidentiary backing.
- Integrated Provenance: We combine post-hoc detection with proactive spectral watermarking and cryptographic C2PA manifests.
- Security-First Architecture: Built with JWT authentication, rate limiting, and automatic temporary file cleanup.


SECTION 17 — LIMITATIONS

To remain technically rigorous, we acknowledge the current limitations of our platform:

1. Probabilistic Nature: Deepfake detection is inherently probabilistic. No model can guarantee one-hundred percent accuracy across unknown future voice synthesizers.
2. Acoustic Noise Sensitivity: Extreme background noise, low-bitrate phone compression, or heavy room reverb can degrade feature quality and affect confidence scores.
3. Computational Overhead: Large transformer models like XLS-R-300M require significant GPU memory or CPU compute power during real-time inference.
4. Evolving Attack Vectors: Adversarial perturbations designed to fool neural classifiers require continuous model updates and retreading.

Recognizing these limitations reinforces why a multi-layered defense model is essential.
